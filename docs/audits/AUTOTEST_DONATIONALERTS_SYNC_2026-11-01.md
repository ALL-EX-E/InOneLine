# AUTO-TEST-002F — DonationAlerts: доставка событий, время реакции и синхронизация UI

**Основание:** 01.11.2026 пользователь прислал скрин DonationAlerts и принятый `InOneLine_AutoTest_20261101_131807.zip` (v1.5: 50 PASS / 0 FAIL / 2 SKIP) и подтвердил, что ручная кнопка «Добавить сообщение» вызывает создание записи/начисление в InOneLine, но возможны задержки и несогласованность списков/истории.

## Источники и осторожность
- Скрин показывает панель `donationalerts.com/dashboard/activity-feed/donations` и зелёный тост «Сообщение было удалено успешно!». Он **не** содержит ID/времени создания события, не доказывает отправку WebSocket push, время появления события или его отмену в базе.
- Присланный ZIP доказывает 27/27 sandbox PASS, реальный Twitch PASS, штатный запуск/закрытие, 15 HTTP 200, но `donationalerts_live_donation` **SKIP**. Не считать ручное «Добавить сообщение» реальным оплаченным донатом.
- Исходный код `DonationAlertsRuntime._run_connection` выполняет websocket handshake + `service.catch_up()`, а затем `service.process_donation` в **фоновом Python thread**. `DonationAlertsDonationService.process_donation` сохраняет в SQLite и продвигает cursor, но не вызывает сигнал/уведомление `MainWindow.notify_game_data_changed`; UI вкладок обновляется через `_refresh_visible_or_mark_dirty` только при явном вызове, F5 или другом локальном изменении. Это **гипотеза реального дефекта** пока не подтверждена воспроизводимым Windows-тестом.
- `MainWindow._handle_tab_changed` обновляет отложенные грязные вкладки, но не обновляет любую вкладку всегда при открытии. `CompletedAuctionHistoryTab` содержит **завершённые аукционы**; не всякое начисление без аукциона обязано создавать строку там. `LogTab` и `external_events` — отдельные источники проверки события.
- `catch_up()` REST выполняется на подключении/переподключении, в основном websocket receive loop нет периодического REST. Значит, потерянный push **может** ожидать переподключения; проверить с имитацией провайдера, не приписывать реальной сети до логов.

## План диагностик, прежде чем менять runtime
1. Тест в отдельной временной SQLite, с программно поднятым Qt/MainWindow, открытым `Публичным списком`. Отключить реальную DonationAlerts сеть тестового окна, подключить synthetic service, подать нормализованное валидное событие через **настоящий** `process_donation` (не прямой `db.update_game`). Отметить момент входа, момент записи `external_events`+`contributions`+`games`, момент видимого обновления каждой из открытых/скрытых вкладок; событие должно появиться без F5 за согласованный разумный локальный срок (напр., 1 с после commit). Если нет — **FAIL**, не маскировать.
2. Повторить тот же ID: ровно одно начисление, один след события, один результат; повторный ID — duplicate.
3. Измерить и отдельно записать причинные стадии в ms: доставлено в процесс → обработано → SQLite commit → UI; на внешней DonationAlerts стороне нет гарантий отправки мгновенно. Проверка локальной задержки не равна времени доставки по сети.
4. Отдельная управляемая имитация WebSocket/REST (без реального аккаунта): пропущенный push/переподключение и порядок ID, чтобы установить, возможен ли пропуск; безопасное повторное получение не должно удваивать начисления.
5. **Необязательный живой операторский шаг** в будущей v1.6: пользователь вручную создаёт сообщение DonationAlerts, если это разрешено интерфейсом сервиса; мы не создаём донат, не отправляем HTTP запросы от его имени и не читаем ключи. Диагностика фиксирует только timestamp начала ожидания, count/status/времена локального события и готовности интерфейса, без имени, текста, токена, исходного payload и содержимого SQLite. Удаление сообщения в интерфейсе провайдера отдельно **не доказывает** откат начисления; не придумывать rollback.
6. До изучения регрессий — **не менять боевой runtime**, `main`, PERF-02B, R06 и принятую v1.5. Подтвержденные FAIL оформить с ожидаемым/фактическим, отдельным предложением исправления, затем только после согласованного поведения — исправление, Windows CI, установщик и ручная приёмка.

**Статус:** план до кода; доказательство дефекта и данные локальных задержек ожидаются.
