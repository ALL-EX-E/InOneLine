# AUTO-TEST-002F — DonationAlerts: доставка событий, время реакции и синхронизация UI

**Основание:** 01.11.2026 пользователь прислал скрин DonationAlerts и принятый `InOneLine_AutoTest_20261101_131807.zip` (v1.5: 50 PASS / 0 FAIL / 2 SKIP) и подтвердил, что ручная кнопка «Добавить сообщение» вызывает создание записи/начисление в InOneLine, но возможны задержки и несогласованность списков/истории.

## Источники и осторожность
- Скрин показывает панель `donationalerts.com/dashboard/activity-feed/donations` и зелёный тост «Сообщение было удалено успешно!». Он **не** содержит ID/времени создания события, не доказывает отправку WebSocket push, время появления события или его отмену в базе.
- Присланный ZIP доказывает 27/27 sandbox PASS, реальный Twitch PASS, штатный запуск/закрытие, 15 HTTP 200, но `donationalerts_live_donation` **SKIP**. Не считать ручное «Добавить сообщение» реальным оплаченным донатом.
- Исходный код `DonationAlertsRuntime._run_connection` выполняет websocket handshake + `service.catch_up()`, а затем `service.process_donation` в **фоновом Python thread**. `DonationAlertsDonationService.process_donation` сохраняет в SQLite и продвигает cursor, но не вызывает сигнал/уведомление `MainWindow.notify_game_data_changed`; UI вкладок обновляется через `_refresh_visible_or_mark_dirty` только при явном вызове, F5 или другом локальном изменении. Это **гипотеза реального дефекта** пока не подтверждена воспроизводимым Windows-тестом.
- `MainWindow._handle_tab_changed` обновляет отложенные грязные вкладки, но не обновляет любую вкладку всегда при открытии. `CompletedAuctionHistoryTab` содержит **завершённые аукционы**; не всякое начисление без аукциона обязано создавать строку там. `LogTab` и `external_events` — отдельные источники проверки события.
- `catch_up()` REST выполняется на подключении/переподключении, в основном websocket receive loop нет периодического REST. Значит, потерянный push **может** ожидать переподключения; проверить с имитацией провайдера, не приписывать реальной сети до логов.

## План диагностик, прежде чем менять runtime
1. Тест в отдельной временной SQLite, с программно поднятым Qt/MainWindow, открытым `Публичным списком`. Отключить реальную DonationAlerts сеть тестового окна, подключить synthetic service, подать нормализованное валидное событие через **настоящий** `process_donation` (не прямой `db.update_game`). Отметить момент входа, момент записи `external_events`+`contributions`+`games`, момент видимого обновления каждой из открытых/скрытых вкладок; событие должно появиться без F5 за согласованный разумный локальный срок (напр., 1 с после commit). Если нет — **FAIL**, не маскировать.
2. Повторить тот же ID: ровно одно начисление, один след события, один результат; повторный ID — duplicate.
3. Измерить и отдельно записать причинные стадии в ms: доставлено в процесс → обработано → SQLite commit → UI; на внешней DonationAlerts стороне нет гарантий отправки мгновенно. Проверка локальной задержки не равна времени доставки по сети.
4. Отдельная управляемая имитация WebSocket/REST (без реального аккаунта): пропущенный push/переподключение и порядок ID, чтобы установить, возможен ли пропуск; безопасное повторное получение не должно удваивать начисления.
5. **Необязательный живой операторский шаг** в будущей v1.6: пользователь вручную создаёт сообщение DonationAlerts, если это разрешено интерфейсом сервиса; мы не создаём донат, не отправляем HTTP запросы от его имени и не читаем ключи. Диагностика фиксирует только timestamp начала ожидания, count/status/времена локального события и готовности интерфейса, без имени, текста, токена, исходного payload и содержимого SQLite. Удаление сообщения в интерфейсе провайдера отдельно **не доказывает** откат начисления; не придумывать rollback.
6. До изучения регрессий — **не менять боевой runtime**, `main`, PERF-02B, R06 и принятую v1.5. Подтвержденные FAIL оформить с ожидаемым/фактическим, отдельным предложением исправления, затем только после согласованного поведения — исправление, Windows CI, установщик и ручная приёмка.

**Статус:** план до кода; доказательство дефекта и данные локальных задержек ожидаются.

**Следующее действие:** отдельно согласовать требуемую скорость/UI приёмку и безопасное Qt cross-thread уведомление. Добавить полноценную непрерывную локальную сверку и user-initiated DA test по этапам, затем исправлять runtime отдельно. `main` и принятая AutoTest v1.5 не менялись. Удаление сообщения в Dashboard не равно заявленному отменённому денежному событию; в DB нельзя автоматически откатывать начисление без доказанного корректирующего события/отдельного согласованного правила.

## Разрешённое исправление DA-SYNC-001 — ожидаемый контракт

**01.11.2026 пользователь согласовал «Делаем» после подтверждённого Windows тестом рассогласования SQLite/видимого Public до F5.** Исправление ведём в `fix/donationalerts-qt-refresh-20261101`, отдельно от принятой версии `audit/operator-autotest-public-20261101`, `main`, PERF-02B/R06.

**Контракт:**
1. После **успешной атомарной обработки** нового события `DonationAlertsDonationService.process_donation` и фиксации курсора инициировать UI-инвалидацию, не теряя/не дублируя баллы. При отсутствии callback (в чистом sandbox) прежнее поведение сохраняется. Не вызывать уведомление до commit. Дублированный ID не должен вызывать лишнее обновление.
2. Фоновый `DonationAlertsRuntime` **не имеет права** менять Qt UI напрямую; уведомление из любого Python thread передаётся только Qt signal с `Qt.QueuedConnection` в GUI thread. `MainWindow.notify_game_data_changed` сохраняет существующие lazy-таблицы, перерисовывает лишь активную, маркирует остальные dirty, обновляет зеркала XLSX через прежние debounce; коалесцировать множественные события за одну итерацию Qt для защиты от пачек.
3. Во время принятого закрытия (`_exit_accepted`) новые UI-обновления прекращаются; штатный shutdown/принятые PERF-01/PERF-02A гарантии неизменны.
4. Диагностика должна проверять **из отдельного Python background thread**: сохранение события и вкладку `Публичный список` без F5, открытие ранее скрытого `Список` и `Журнал` с catch-up, отсутствие ложной записи в `Историю завершённых аукционов` для событий вне аукциона, дедупликацию одного event ID. Проверка не использует настоящие сети или токены.
5. Отдельный необязательный операторский тест: вручную создать **неоплачиваемое** сообщение в кабинете DonationAlerts, измерять время с начала ожидания до появления нового события в чтении API, **без реальных платежей**; не включать личные сообщения, токены, usernames или ID в ZIP. Отсутствие нового события отмечать честным FAIL/SKIP (отдельно от synthetic PASS); при отсутствии подходящего сообщения шаг можно пропустить. Из одного наблюдения не делать статистических выводов.
6. Все 27 прежних sandbox сценариев, native GUI/XLSX regression, graceful close и Windows frozen должны быть успешны. До CI/ручного ZIP новые баги не считать устранёнными.

**План зафиксирован до изменения кода.**


## Исправление DA-SYNC-001: CI + комплект v1.6

**Реализация:** функциональные изменения ограничены `streaming_manager/donationalerts_runtime.py` и `streaming_manager/views/main_window.py`. После успешно обработанного и зафиксированного в БД нового DonationAlerts события вызывается необязательный `on_event_applied`. Из фонового Python network thread передаётся `MainWindow.donationEventApplied.emit`, соединённый с `_schedule_donation_view_refresh` через `Qt.ConnectionType.QueuedConnection`. Обновление коалесцируется через `QTimer.singleShot(0, ...)` в GUI thread: `notify_game_data_changed` вызывает существующую инвалидацию списка/публичного списка/аукциона/журнала/стрима и синхронизацию подключённых XLSX с прежним debounce. Событие с повторным ID не вызывает двойного начисления; `_exit_accepted` блокирует обновления при закрытии. Доступ из фонового потока к Qt виджетам отсутствует. Функции REST/WebSocket доставки в этом изменении не корректировались.

**Синтетическая воспроизводимая диагностика Windows:** [run 41281531063](https://github.com/ALL-EX-E/InOneLine/actions/runs/41281531063), **SUCCESS**. Новое событие из реального Python background thread → SQLite commit **94 мс** → открытый Public без F5 спустя **125 мс** → скрытый List/Log обновляются после открытия (PASS), завершённая история аукционов не получает ложное событие вне аукциона, дубликат по ID не начисляется. `provider_to_desktop_delivery=NOT_TESTED`: время доставки по Интернету не измерено.

PASS: Windows PowerShell 5.1 parser, PERF-01/PERF-02A regressions, native GUI/XLSX, штатное закрытие frozen EXE и освобождение порта (**0,781 с** на CI; не benchmark нагруженного ПК), Inno Setup и artifact.

**Новый необязательный живой операторский сценарий:** после Twitch-этапа скрипт предлагает самостоятельно (оплата **не** требуется, запросы к DonationAlerts не отправляются тестировщиком) создать сообщение с уникальным заголовком `IOLDA-...` в кабинете DonationAlerts. Путь `/api/public` проверяется до 120 секунд; время измеряется от нажатия Enter перед фактическим кликом пользователя (с человеческой задержкой), затем оператор оценивает без F5 видимость во вкладке Public. Такой операторский тест **может добавить тестовую запись в реальный список**, поэтому необходим backup и явный отказ `N`, если это нежелательно. ZIP содержит только результат/миллисекунды без ID, названия, текста, токена или персональных событий. Настоящий платёжный донат по-прежнему `SKIP`.

**Контроль ручной проверки:** сохранить резервную копию пользовательской БД и настроек → установить кандидата v1.6 → заменить PS1/CMD → полностью закрыть InOneLine → запустить CMD → отправить необязательное Twitch-сообщение → принять/отклонить неоплачиваемое сообщение DonationAlerts → закрыть GUI обычным X → прислать ZIP с рабочего стола. При успешном прохождении необязательных Twitch и DonationAlerts-сообщений ожидаем **53 PASS / 0 FAIL / 2 SKIP** (прежние 50 PASS + 1 sandbox + 2 живых DA пункта; channel points и оплаченный донат остаются SKIP); при пропуске необязательных шагов будут дополнительные SKIP. Не объявлять пользовательскую приёмку v1.6 до полученного ZIP.

**Ограничения:** не установлены времена доставки в реальной сети и механизм пропусков WebSocket, не проверены реальные оплаченные донаты, обработка удалённых в кабинете сообщений, реальные конфликтующие XLSX-клиенты и все сценарии журнала. Технический `Publication wording gate` по историческим документам R06 не включён в принятие этой задачи и остаётся отдельным незакрытым пунктом. Ветка `main`, принятая AutoTest v1.5 и PERF-02B не менялись.
