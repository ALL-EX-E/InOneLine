## Что действительно делает текущий код

- Неизвестная валюта отправляет `process_donation` в `pending_conversions.awaiting_rate`; `set_conversion_rate` пересчитывает в `awaiting_manual_apply`, **баллы не добавляются автоматически**. Только `apply_pending_conversion_event` создаёт либо доначисляет запись и пишет `contributions`, `external_events`, `change_log`. `reject_pending_conversion_event` навсегда отменяет и сохраняет след.
- Если у `pending` есть привязка к активному `max_amount`, ручное применение идёт в исходный аукцион. После `finish_auction` (`winner_selected` или `tie_break_required`) **до подтверждения** сохраняется право исправить результат исходного Max Amount. `confirm_auction_winner` обязан запрещать подтверждение с необработанным `pending`. Корректировка может изменить победителя, но не перезапускает аукционный таймер.
- `weighted_wheel` и формат «Выбывание»: `start_in_wheel_mode=True` создаёт сразу `awaiting_wheel`, а не running. Поступление вне running с прежним названием направляется в обычную запись, но не меняет `auction_entries` колеса; это следует из существующего правила выбора running по исходному времени. Начисление после закрытия нельзя переносить к другому аукциону.
- `DonationAlertsDonationService.catch_up` получает REST-пачку, сортирует увиденные ID по возрастанию и вызывает обычный обработчик, чтобы не пропустить меньшие ID **внутри полученной пачки**. Дедупликация `external_events` и курсора обязательна.
- **Выявленный по коду риск DA-NET-002 (отдельная проверка):** обработчик немедленно отвергает любое событие `id <= last_seen_id`, не проверяя, поступало ли оно прежде. При WebSocket-доставке 102 **раньше** 101 возможна потеря начисления 101. Не менять политику курсора молча; отдельно воспроизвести и согласовать исправление, потому что это может влиять на защиту от повторов.

## Первые 7 изолированных сценариев (B1 / кандидат AutoTest v1.8)

1. Неизвестная валюта и новое название **вне** аукциона: очередь → установка курса → явное применение → одна новая постоянная запись, одна contribution, исходный event `processed`, повторное применение невозможно.
2. Неизвестная валюта и **существующая** запись вне аукциона: pending, сохранение прежних баллов до применения, затем прибавление по курсу без нового лота, точные game_id и contribution.
3. Отклонение queued: статус `cancelled`, отсутствие баллов и contributions, повторный ID не приводит к начислению и повторно применять/отменять нельзя.
4. `max_amount` в статусе running: queued привязано к текущей сессии; применение после установки курса увеличивает запись и `auction_entries.bid_sm_points` с корректным weight и не создаёт дублей.
5. `max_amount` после 00:00 (`winner_selected`): pending блокирует финальное подтверждение; применение может поменять победителя, не перезапуская таймер; последующее подтверждение завершает тот же исходный аукцион, вкладка исторических результатов остаётся согласованной.
6. Прямое взвешенное колесо `awaiting_wheel`: событие по существующей постоянной записи вне running не меняет `auction_entries`/колесо, привязывается к исходной записи вне аукциона; проверка для обычного формата (режим «Выбывание» — следующая партия).
7. REST catch-up: хотя пачка приходит newest-first, обработка ID 101/102/103 должна идти в возрастающем порядке после cursor 100, давать ровно 3 начисления; повторная REST-пачка не добавляет баллы/строки.
