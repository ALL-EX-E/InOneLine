## Карта механизмов из кода (все отдельные ветви и риски)

`DonationAlertsDonationService.process_donation` нормализует `id,amount,currency,username,message,created_at`, выбирает **исторический** аукцион по `created_at`, затем передаёт событие в `IntegrationManager.accept_normalized_event` и атомарный B3 `db.process_normalized_integration_event`; после транзакции двигает high-water cursor. B3 выбирает сценарий по историческому времени, наличию лота/названия, архиву, статусу аукциона, валюте/конвертации и ID.

**Вне аукциона:**
- Уже существующая неархивная запись с тем же нормализованным названием получает баллы `прошлые + сумма × курс`; новую запись не создавать; событие и contribution привязаны к старой.
- Новое непустое название создаёт обычную постоянную запись и начисляет баллы; повторное пожертвование на неё добавляет баллы.
- Название архивной/временной записи не должно приводить к обходному созданию дубликата: `inapplicable`.
- Пустое сообщение **вне** аукциона не создаёт лот; `missing_target` в истории.
- Некорректные ID, отрицательная или нечисловая сумма, неверная трёхбуквенная валюта отклоняются без побочных эффектов; нулевая сумма с не-положительным результатом `inapplicable` и без начисления.
- Для валюты без курса: `awaiting_rate`, запись в очередь `pending_conversions`, **не создавать** новый лот и не начислять до явного применения.

**Во время аукциона:**
- Название существующего лота — начисление в этой сессии, сохранение contribution/суммы/веса; повторное событие по новому ID того же лота добавляет, старый ID — нет.
- Новое название создаёт аукционный лот, а не скрыто новый постоянный лот вне аукциона.
- Пустой текст создаёт последовательные `Без текста 1`, `Без текста 2` (UI-087), при повторном ID ordinal не должен меняться.
- Отсутствующая валюта → pending для соответствующего аукциона; неизвестная ставка не должна попадать в начисления.
- При **задержанном** событии нельзя начислять в более поздний аукцион: выбирать по `created_at`. При уже недоступной исходной сессии корректировка имеет отдельный предписанный workflow. Нельзя молча переносить ставку в новый аукцион.
- Ветви `max_amount`, прямое взвешенное колесо и на выбывание, окончания таймера/подтверждения победителя имеют отдельные зависимости, которые покрывать поэтапно.

**Поступление/синхронизация:**
- Дубликаты cursor + `external_events` по source+ID, смена интеграции, сохранение курса, REST catch-up на reconnect, исходный timestamp, таймауты сети, частичные ошибки и замороженный Qt-процесс — отдельная матрица надёжности.
- Снятие/удаление сообщения в кабинете DonationAlerts НЕ объявлено refund/rollback в текущем B3; отдельно выяснить требуемое поведение и поддержку провайдера.

## Первая исполняемая партия AUTO-TEST-002G A (v1.7)

Новые независимые sandbox-тесты на **реальном** `process_donation` и SQLite:
1. существующее название, повторные новые ID и атомарные связи event/contribution → **не создаёт дубликат записи**;
2. новое название → создание и повторное начисление той же записи;
3. архивное название → `inapplicable`, без начисления и дубликатов;
4. пустое сообщение вне аукциона → `inapplicable`, без `Без текста` вне сессии;
5. нулевая сумма → `inapplicable`, отсутствие contribution/баллов;
6. незнакомая валюта → `awaiting_rate`, событие и очередь без начисления/появления нового лота;
7. running max_amount → пополнение уже участвующего лота и данных `auction_entries`;
8. running max_amount → новый аукционный лот, наличие правильной привязки к сессии;
9. running max_amount без текста → уникальные `Без текста 1/2`, защита ordinal от повторного ID;
10. задержанная доставка, источник **вне** аукциона, а текущий аукцион уже открыт → начисление вне текущего аукциона;
11. уже отменённая исходная сессия → `inapplicable`, без начисления в чужую сессию.

Все проверки фиксируют конкретные ID, баллы, `auction_id`, количество contribution и сохранение остальных данных, не только HTTP 200 или статус. Тесты прошлого пакета **28/28 сохраняются**. Цель v1.7: **39/39** sandbox PASS плюс native GUI/XLSX/PERF Windows regressions, frozen EXE/installer/пользовательский ZIP. Если механика противоречит ожиданию, **FAIL** и разбор; не адаптировать ожидание под дефект без согласования.
