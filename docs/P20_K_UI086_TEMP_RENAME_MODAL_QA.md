# UI-086 / P20-K — компактная кнопка и двухступенчатое подтверждение переименования

**Отдельный QA-кандидат, пока не принят.** После установки P20-J пользователь написал: «Всё работает. Всё принимаю. Но реализация хромает», и предложил конкретное упрощение интерфейса. P20-J признан функционально верным и переносится в `main` отдельным exact-tested-blob promotion PR #308 после полного независимого Windows CI. P20-K меняет **только UX**, не бизнес-логику.

## Требуемое поведение

- Отдельная строка «Название временного лота» с полем ввода и встроенной кнопкой на вкладке «Проведение» **удаляется** полностью.
- Кнопка **«Переименовать»** находится в том же горизонтальном ряду, что «Добавить», «Уменьшить» и «Удалить лот». Она доступна только при выделенном временном лоте исходного аукциона **«Максимальная сумма»** после 00:00, если результат предварительный и колесо не заморожено; для постоянных/чужих/удалённых/подтверждённых лотов она скрыта/запрещена.
- Нажатие открывает **модальное окно** «Переименовать лот». Вверху — **текущее название выбранного лота** в поле только для чтения. Ниже — строка **«Новое название»**, изначально заполненная текущим названием с выделенным текстом для быстрого изменения. Внизу — кнопки **«Переименовать»** и **«Отмена»**.
- «Отмена», закрытие окна или Esc ничего не сохраняют и не показывают дополнительный запрос.
- После нажатия «Переименовать» и проверки непустого/изменённого текста появляется **отдельный запрос**: «Вы точно хотите переименовать выбранный лот?» с указанием старого и нового названий, кнопками **Да / Нет**, по умолчанию **Нет**. Нажатие Нет не меняет базу.
- Только после выбора Да вызывается **принятый и протестированный P20-J backend**. Повторно проверяются auction_id, временный лот, pending-конвертации, внешние поступления, отсутствующие/удалённые/архивные/чужие записи, совпадающие названия, неподтверждённый результат и колесо. Ошибки отображаются пользователю; никаких частичных изменений.
- После успешной операции обновляются таблица и журнал и сохраняется выбранный `game_id`. Не изменяются SM-баллы, записи ставок, время 00:00, колесо, общие настройки и OBS.
- Версия **1.0.8**, SQLite schema, RNG, звуковые виджеты, логика импорта и основная база игр без изменений.

## CI Windows

Сохранены все старые P20-A–J regression smoke. В `tools/auction_post_expiry_temporary_rename_smoke.py` старый тест inline UI заменён модальным: проверяется положение кнопки в `bid_widget`, отсутствие inline-поля, отображение текущего названия, новое название, вызов подтверждения с **default No**, успешное переименование, скрытие для постоянного лота и после подтверждения аукциона. Добавлен второй сценарий: **закрытие модального окна и нажатие Нет** оставляют снимок SQLite без изменений и не порождают лишних запросов. Специальный P20-K шаг в full Windows workflow запускает оба сценария отдельно, дополнительно к полному регрессионному набору, OBS/Chromium, Inno Setup и silent startup. Отдельный `Publication wording gate` обязателен.

## Ручной QA на Windows

1. Установить новую QA 1.0.8 поверх принятой P20-J. Убедиться, что прежней дополнительной строки переименования больше нет.
2. В «Максимальная сумма» после 00:00 выделить временный лот. В ряду с «Добавить / Уменьшить / Удалить лот» появляется кнопка **«Переименовать»**. Для постоянного лота её нет.
3. Открыть окно: показано правильное старое название, ниже редактируемое новое. Проверить **Отмена** — никаких изменений.
4. Ввести новое название → «Переименовать» → **Нет** на втором подтверждении — ничего не меняется. Повторить → **Да** — лот переименовывается, game_id и баллы не меняются, таймер остаётся на 00:00.
5. Попробовать совпадение с существующей, архивной, временной либо удалённой игрой. Программа должна отклонить изменение без дублей и без ошибок. После подтверждения победителя или перехода к колесу переименование недоступно.
6. Проверить минимальную и максимальную ширину окна, F5, список, музыку, OBS и сохранение настроек.

Только полный Windows SUCCESS + wording SUCCESS → точный проверенный ZIP на Google Drive `Обзор_UI_1.0.8` со сверенным SHA-256 и CRC → ручная приёмка пользователя → чистый exact-tested-blob promotion. QA PR не объединять и публичный релиз не создавать до приёмки.
