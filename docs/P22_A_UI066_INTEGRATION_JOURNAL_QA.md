# P22-A / UI-066 — понятная судьба поступлений интеграций в общем «Журнале»

**Изолированный QA-кандидат, до ручного подтверждения не принят и не объединён с `main`.** Это первый узкий этап согласованного P22; цель — исходный UI-066 из `docs/ACTIVE_REVIEW_LEDGER.md`, без самостоятельных новых функций.

## Объём

- В существующем `Журнал` сохраняются все исходные `change_log` rows с прежними `id DESC`, последними 500 без поиска, полным поиском по raw + видимому тексту, асинхронным `FunctionWorker`, F5/dirty-tab и read-only моделью.
- При чтении того же `change_log` к строкам `entity_type=integration_event` добавляется только `external_events.payload_json` по исходному `external_events.id`. SQL `LEFT JOIN` идёт по исходному PK и не дублирует строки. Никаких новых таблиц, migration, публикации данных или независимого provider-журнала нет.
- В существующей строке события теперь понятно видны: сервис, имя отправителя (или `Аноним`), исходная сумма/единица, лот, ID внешнего события и результат; у начисленного — баллы и куда именно пошли деньги (`В аукцион #ID` либо `В основной список`); у ожидающего — `ОЖИДАЕТ КОНВЕРТАЦИИ`; у неприменённого — причина на русском.
- У известного отказа `target_game_archived` оператор увидит `Лот находится в архиве`; аналогично для отсутствующего, временного или неназванного лота, закрытого исходного аукциона и неположительных баллов. Технический reason остаётся доступен через существующий raw full-search.
- Не показывать raw `provider_metadata`/payload как пользовательский текст: поля с секретами не попадают в presentation. Сохраняется уже принятое скрытие конфиденциальных данных в общей интеграции.
- Новые UI labels действуют только для `integration_event` в данном узком этапе. Полный единый перевод остальных объектов/действий и тёмные чередующиеся строки `QTableView` — уже утверждённый **UI-081**, отдельная последующая задача; здесь их не дублировать.
- Не менять сериализацию исходного события, дедуп, сами начисления, суммы, таймер, колёса, OBS, backend интеграций, SQL schema 19, версию **1.0.8** или публичный релиз.

## Автоматическая проверка Windows

`tools/integration_journal_visibility_smoke.py`:

1. Успешное начисление в постоянный список: source/sender/original amount/lot/points/route, raw event ID видны; повторная доставка не создаёт нового audit/credit.
2. Событие архивного лота не исчезает: `НЕ НАЧИСЛЕНО`, читаемая причина `Лот находится в архиве`, баллы не начислены; поиск по русскому тексту и сырому reason работает.
3. Неизвестная unit: `ОЖИДАЕТ КУРСА`, нет баллов; ручное `Не применять` оставляет в журнале ещё одну отдельную осознанную отметку.
4. Начисление в живой аукцион: указан `В аукцион #ID`, а не `В основной список`.

Полный нативный Windows CI также проверяет прежние P21-A, P20, Qt/Chromium/OBS, Inno Setup installer + silent startup и Publication wording gate.

## Ручной Windows-чек-лист

1. Установить P22-A QA на существующую 1.0.8, проверить сохранение базы, настроек, текущих лотов.
2. Открыть `Журнал`: интеграционные события, уже записанные ранее, показывают русские исходы, сервис, источник, сумму, цель; обычные записи игр/аукционов не исчезли.
3. Для начисленного события видны баллы и **действительное направление** — `В аукцион #...` либо `В основной список`.
4. Для отказанного видны `НЕ НАЧИСЛЕНО` и причина; для ожидающего курса — `ОЖИДАЕТ КУРСА`; прошлое `Не применять` различается с автоматическим отказом. Не отправлять реальные донаты специально для QA — тесты изолированные.
5. Поле поиска: находить событие по ID, названию лота, русскому описанию, английскому technical reason; выборка без поиска остаётся ограниченной последними 500, поиск по полной истории.
6. F5, сортировка newest-first, перенос окон между размерами и обычные OBS/музыка/конвертация не меняются; никакой новой вкладки/Журнала нет.
