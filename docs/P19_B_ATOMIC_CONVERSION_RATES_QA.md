# P19-B / UI-085 — атомарное сохранение курсов конвертации

Дата: 2026-10-19. Основа: принятый вручную P19-A, перенесённый в `main` через PR #265, merge `333adeca80bcc37b0e5d7c0b2704e30bae4c2a9a`; исходный QA-код P19-A не изменялся. Независимый функциональный пакет после P19-A.

## Фактическое изменение

Раньше `Настройки → Конвертация → Сохранить курсы` вызывала `set_conversion_rate` или `clear_conversion_rate` для каждого поля последовательно. Если позднее поле содержало ошибку, значения предыдущих строк уже записывались, частично изменяя курсы и состояния ожидающих событий.

Теперь `save_conversion_settings()` передаёт все видимые поля в существующий Database API `set_conversion_rates_atomic`. Этот метод сначала **проверяет все исходные единицы, типы, значения, отсутствие дубликатов**, не изменяя SQLite. Если хотя бы один курс невалиден, возвращается ошибка и **все введённые тексты остаются в полях**, а курсы в SQLite не меняются.

Если вся проверка успешна, **ровно одна SQLite transaction** сохраняет существующие ключи `settings`, metadata `conversion_units`, audit `change_log` и одновременно пересчитывает статусы `pending_conversions` и `external_events` через прежнюю функцию, вынесенную для совместного использования одного `conn`. При ошибке записи в любой строке откатываются **и курсы, и метаданные, и статусы, и аудит**. Только после успешного commit UI нормализует текст и обновляет очередь. Двойного хранилища и миграции нет.

Семантика сохранена: пустой RUB означает курс `1`; пустая другая единица означает убрать курс, без удаления зарегистрированной единицы; валидные дробные значения принимают запятую, хранятся с точкой. Уже начисленные баллы не пересчитываются. После установки курса ожидающее событие **не начисляется автоматически**, а остаётся для явного `Применить`. Старые индивидуальные API `set_conversion_rate` и `clear_conversion_rate` не изменены.

Исключены из этого пакета: название для pending с `game_id=NULL`, колонка `Время`, `Не применять`, draft при смене service capabilities, UI-086 auction pending gate и прочие отдельные UI-085 пункты.

## Ручная проверка Windows — пять сценариев

1. Зафиксировать настоящие курсы RUB и ещё одной доступной единицы; при необходимости создать резервную копию базы. Изменить **два или более** курса, второй ввести заведомо неверным текстом. Нажать `Сохранить курсы`: понятное предупреждение, **не должно сохраниться ни одно новое значение**.
2. Не исправляя и не переключая вкладку, проверить, что оба введённых значения **остались в полях**. Исправить ошибочный курс и сохранить: только после этого должны сохраниться **все валидные значения одновременно**.
3. Очистить RUB и сохранить: он нормализуется к `1`. Очистить курс другой единицы: она остаётся в списке, но курс становится «не настроено». Важное: вернуть исходные значения и повторно сохранить, если проверка проводится на реальных настройках.
4. Если в очереди уже есть событие с неизвестным курсом, задать курс и сохранить: событие должно перейти в готовность к ручному применению, показать предварительный расчёт, **но не начислиться без `Применить`**. Если таких событий нет, создавать их специально в основном профиле не требуется; автоматический тест проверяет оба направления статусов.
5. Перейти между вкладками, обновить F5 и перезапустить приложение: сохранённые курсы должны остаться. Проверить обычные интеграции, отсутствие двойного начисления, базовую работу аукциона и OBS. Не менять намеренно уже прошедший аукцион/историю.

Автоматический Windows Qt/SQLite smoke `tools/conversion_atomic_rates_smoke.py` проверяет ошибку второй строки без частичного сохранения; success с RUB=1 и удалением другого курса; синхронность statuses в `pending_conversions` и `external_events`; искусственный сбой второй SQL-операции и откат settings/audit/units/pending; отклонение дубликатов и неположительных значений; сохранность несохранённого текста UI после ошибки и повторное успешное сохранение.
