# P20-B / UI-086 — применение ожидающего поступления после 00:00 к исходному существующему лоту

**Изолированный черновик QA, НЕ принят.** Версия 1.0.8; без публичного релиза и изменений схемы БД. Следует после ручной приёмки P20-A.

## Точная граница этапа

Если событие было привязано к исходному аукциону в момент поступления, но курс стал известен только после 00:00, теперь явная кнопка «Применить» может **в той же исходной сессии Max Amount** начислить баллы **существующему лоту этой сессии**, пока результат предварительный: status = winner_selected либо tie_break_required. Считается только привязка pending_conversions.auction_id, а не «текущий» или новый аукцион. Дубли source + external_event_id сохраняют прежнюю защиту exactly-once.

Начисление в одной SQLite-транзакции:
- находит существующий lot/entry **именно по source auction_id** и stored game ID или точному нормализованному названию;
- увеличивает auction_entries.bid_sm_points/weight и games.sm_points; в той же транзакции создаёт обычный contribution, переводит pending в applied и event в processed, пишет audit;
- заново включает ранее неактивные лоты, которые могли быть исключены при предварительной ничьей, и **пересчитывает лидера/ничью по всем лотам исходной сессии**;
- результат winner_selected / tie_break_required, winner_game_id и пометки result пересчитываются, но **прошедший таймер не запускается заново**, deadline_at, remaining_ms и finished_at не изменяются;
- P20-A gate продолжает блокировать подтверждение победителя и tie-wheel, пока **другие** события той же сессии не обработаны; explicit «Не применять» остаётся доступно.

**Не смешивать с неготовой частью UI-086:** новый title-only lot, которого ещё нет среди entries исходного аукциона, после 00:00 этим пунктом НЕ создаётся автоматически: кнопка Apply остаётся выключена, backend даёт безопасное сообщение, event остаётся pending. Создание нового source-auction лота после 00:00 и общий weighted-wheel freeze guard — **следующие отдельные этапы P20-C+**. Система не переписывает подтверждённые/cancelled/legacy-сессии и не переназначает поступление новому аукциону. Обычная обработка живых running-сессий, внеаукционные события, таймер, музыка и OBS не меняются.

## Пять ручных сценариев Windows

1. Если есть pending от исходного Max Amount, чей отсчёт уже закончился, но победитель ещё **не подтверждён**, после сохранения курса появляется доступное «Применить», когда цель — существующий лот исходной сессии. Без реального события создавать донат ради QA не нужно: заполненные сценарии проверяются временной SQLite базой.
2. После явного «Применить» исходная сессия обновляет баллы и предварительного лидера: поздний credit может сменить победителя или создать/снять ничью; до разрешения всех pending работает предупреждение P20-A.
3. Таймер остаётся на 00:00. История external event, source-auction ID, contribution и журнал сохраняются. Повторно применить тот же ID нельзя.
4. У уже подтверждённого/отменённого аукциона результат не пересчитывается и событие не переходит в новый активный аукцион. Для title-only события с отсутствующим среди source entries лотом Apply после 00:00 пока недоступно; «Не применять» продолжает работать.
5. Проверь F5, минимальную ширину окна, предварительный лидер/ничью на «Аукцион → Проведение», кнопки подтверждения/колеса, OBS/музыку/таймер и обычное применение внеаукционных событий.

Native Windows regression tools/auction_pending_post_expiry_correction_smoke.py — 5 тестов: смена лидера без перезапуска таймера, late tie пересчёт с восстановлением неактивных entries, создание ничьей+P20-A gate, запрет переписывать closed историю или другую сессию, безопасная блокировка отсутствующего source lot. Все P19-A—G, P20-A и штатные GUI/Chromium/OBS/installer regressions обязательны.
