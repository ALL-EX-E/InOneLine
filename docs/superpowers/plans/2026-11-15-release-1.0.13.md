# InOneLine 1.0.13 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build, verify and stage the accepted Journal fixes as an immutable InOneLine 1.0.13 release candidate, then publish only after a separate installed PASS.

**Architecture:** Keep runtime behavior at accepted `main`; change only release/version metadata, active Windows candidate packaging and release documentation. Native CI remains the builder and verifier; Drive readback and the append-only accepted-release publisher preserve exact bytes.

**Tech Stack:** Python 3.12, PySide6, PyInstaller, Inno Setup, GitHub Actions, Google Drive.

**Spec:** `docs/superpowers/specs/2026-11-15-release-1.0.13-design.md`

## Global Constraints

- Preserve GitHub Release `v1.0.12` and its assets unchanged.
- Set application and installer version to exactly `1.0.13`.
- Keep SQLite schema exactly `21`.
- Do not add an immutable publication request before the user accepts the exact installed 1.0.13 candidate.
- Publish only assets copied from the accepted Actions artifact without rebuilding.

## Review Focus

- No active `1.0.12` assertion may remain in version, installer or candidate packaging paths.
- Historical 1.0.12 records and its immutable publication request must remain unchanged.
- Candidate workflow must emit installer and official source ZIP from the same tested commit.
- Release notes must describe only the accepted Journal corrections and compatibility boundary.
- The artifact presented for manual QA must be proven by size and SHA-256 after Drive readback.
