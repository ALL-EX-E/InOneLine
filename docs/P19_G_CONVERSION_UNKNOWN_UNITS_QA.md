# P19-G / UI-085 #7.1 — новые единицы и очередь конвертации

Изолированный этап после ручной приёмки P19-F. **QA DRAFT / НЕ ПРИНЯТО / НЕ ПЕРЕНОСИТЬ В main / НЕ ПУБЛИКОВАТЬ**. Приложение остаётся 1.0.8.

## Рамки изменения

Принятая backend-основа S1/B3 уже регистрирует незнакомую единицу и создаёт её pending external event **в одной SQLite-транзакции** при событии, прошедшем проверку включённого подключённого провайдера и имеющем пригодную цель:
- новая неизвестная валюта (например, XYZ) появляется в реестре conversion_units и как поле «1 XYZ = ... баллов» благодаря существующей глобальной currency-visibility;
- то же событие появляется в «Ожидают применения», показывает внешний ID, источник, цель, сумму и состояние awaiting_rate;
- нет курса — «Применить» неактивно, игра/лот и contributions не создаются заранее;
- «Сохранить курсы» переводит подходящие события в awaiting_manual_apply и обновляет рассчитанное количество баллов, **не начисляя** автоматически;
- действие «Применить» остаётся явным; «Не применять» сохраняет raw event/dedup/audit.

Новый узкий UI-085 #7.1 fix: **динамическая сервисная единица**, впервые полученная в принятом event от подключённого сервиса, может отсутствовать в заранее объявленном capability list адаптера. Ранее такая unit регистрировалась вместе с pending event, но редактор курсов оставался скрытым, поскольку visibility сверяла только capability keys.

Теперь зарегистрированная сервисная unit видна, **если её исходный service** находится в integration_connections с enabled=1,status=connected, даже когда адаптер не перечислил её статически. При disconnect/disable скрыть специфическую unit из редактора, **но не удалять** сохранённый курс и незавершённые события; при reconnect редактор возвращается. RUB и известные валюты остаются видимыми по прежним правилам.

При очередном обновлении таблицы «Ожидают применения» синхронизируется набор строк курсов; новая unit становится доступной в той же операции обновления (F5, повторный вход во вкладку, инициированный refresh). **Не добавлять периодический polling.** Принятый P19-F сохраняет несохранённые правки при перестройке полей.

Не изменять парсер единиц, source-amount → SM округление, backend credit policy, provider auth, raw provenance, аукционное ограничение UI-086, schema, OBS или таймер.

## Пять сценариев ручной Windows QA

1. Открой Настройки → Конвертация. После **реально пришедшего** допустимого события с незнакомой валютой она должна появиться в курсах пустой строкой, само событие — в «Ожидают применения» с исходным значением и целью. Без курса «Применить» недоступно.
2. Для новой unit, которую провайдер присылает в событиях, но заранее не перечисляет среди возможностей, строка с курсом тоже появляется, пока сервис **подключён и включён**. При отключении её редактор скрывается, но сохранённый курс и pending остаются. После включения редактор возвращается.
3. После сохранения положительного курса «К зачислению» пересчитывается и «Применить» становится доступно при пригодной цели; баллы **не начисляются** без явного Apply. Не создавай реальные донаты специально для QA — заполненные сценарии покрыты временной SQLite базой.
4. Измени RUB **без сохранения**, обнови таблицу или смени вкладку при появлении новой unit: RUB-черновик остаётся, SQLite не изменяется.
5. Проверь F5, минимальную ширину, «Не применять», перезапуск и прежнюю работу OBS/аукциона. Повторный provider ID не создаёт второй pending и не начисляет дважды.

Нативный Windows smoke tools/conversion_unknown_unit_pending_smoke.py создаёт временную SQLite и пять кейсов: новый currency + pending/no-credit; незаявленная service unit + rate/manual-ready без начисления; скрытие при disconnect и восстановление при reconnect; duplicate source+event ID; обновление очереди и сохранение черновика P19-F. Старые Windows P19-A—F, браузерные/OBS/таймерные и Inno-установочные тесты остаются обязательными.
