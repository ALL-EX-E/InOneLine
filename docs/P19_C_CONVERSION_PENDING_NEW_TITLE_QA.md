# P19-C / UI-085 — новая игра в очереди ожидания неизвестного курса

Основа: вручную принятый P19-B / UI-085 и его точный проверенный promotion PR #268. Независимое изменение после P19-B; версия остаётся 1.0.8.

## Проблема

Событие с новым пригодным названием игры и неизвестным курсом сохраняется в `external_events` + `pending_conversions` без создания записи `games` заранее (accepted B3/S1). Таблица `Ожидают применения` до сих пор берёт название только из `games.title` по `game_id`. У такого события `game_id=NULL`, поэтому видимое название «Игра недоступна», и кнопка `Применить` неактивна даже после сохранения курса. При этом backend уже умеет создать/обновить постоянную игру во время явного применения.

## Минимальное исправление

- `_pending_row_to_dict` читает **только ранее сохранённое** `external_events.payload_json.normalized.lot_title` как fallback, если `game_id` ещё нет или название по ID недоступно. Разбор вынесен в маленький общий helper, которым теперь пользуется и существующий backend `apply_pending_conversion_event`, чтобы не разошлись правила выбора названия.
- `can_apply` готовится на стороне Database по действующим предпосылкам: есть сохранённый курс, положительный расчёт, допустимая цель; event с сохранённым source auction ID не может автоматически перейти в другую сессию или постоянный список при закрытии исходной; для существующей игры проверяются архивность и временность вне running аукциона.
- UI выводит фактическое пригодное название и использует `event.can_apply`, а не `game_id`/JOIN, для разрешения кнопки `Применить` и для текста уже существующего диалога подтверждения.
- **Само начисление/создание игры не меняется**: вне аукциона оно происходит только при подтверждённом manual Apply через existing SQL transaction, используется ранее нормализованное название, повторное применение запрещено; при running source auction действует прежняя авторитетная session logic.
- Блокировку позднего применения к *собственной* уже остановленной source auction во время correction-phase и счётчик на `Аукцион → Проведение` составляет **следующий отдельный UI-086**, а не P19-C. Нельзя автоматически приписывать события иному/новому аукциону.
- Нет миграции, новой таблицы, API провайдеров, новых внешних запросов, изменений таймера/колеса/истории или автоматического начисления при сохранении курса.

Файлы: `streaming_manager/db/services.py`, `streaming_manager/views/settings.py`, `tools/conversion_pending_new_title_smoke.py`, Windows workflow gate, этот документ.

## Ручная проверка Windows (пять сценариев)

1. Откройте `Настройки → Конвертация → Ожидают применения`. Если есть событие с новой пригодной игрой и неизвестным курсом, в колонке `Игра` должно быть **настоящее название из события**, а не «Игра недоступна». Если таких событий нет, **не создавайте реальный донат ради теста**: это проверяется автоматическим тестом на чистой SQLite-базе.
2. До сохранения курса кнопка `Применить` для такого события неактивна; начисления нет. После явного сохранения курса появляется рассчитанное число баллов и кнопка становится активной.
3. При наличии тестового ожидающего события нажмите `Применить`, убедитесь, что показан правильный заголовок новой игры и расчёт; подтвердите только если это реальное нужное начисление. После подтверждения игра создаётся/обновляется, событие исчезает из активной очереди и вторично не начисляется. Для отсутствующей очереди достаточно автоматических тестов.
4. Для записи без пригодного названия или с нулевым начислением кнопка остаётся неактивной. Для события закрытого исходного аукциона **без ранее привязанной постоянной игры** кнопка также неактивна; наличие допустимой постоянной игры подчиняется прежним правилам backend. Событие другой сессии не должно прикрепляться к текущему аукциону. Не изменяйте и не переоткрывайте завершённые аукционы ради теста: автоматические проверки покрывают границу.
5. После F5, перехода по вкладкам и перезапуска новые заголовки и состояние очереди сохраняются. Настройки курсов (включая P19-B atomic save), интеграции, аукцион, колесо и OBS не меняются.

Тест `tools/conversion_pending_new_title_smoke.py` проверяет 6 сценариев: title fallback до создания игры; disabled до rate и enabled после; явное применение с созданием/повторным использованием нормализованной постоянной игры и запретом дублей; пустой/повреждённый payload и нулевое начисление; закрытый source auction не превращается в новую игру.
