# P22-B / UI-080 — шаг 2: фактический путь определения победителя в завершённой истории

Статус: отдельный QA-кандидат, НЕ принят пользователем, не объединять до ручной проверки.
Предыдущий шаг удаления сортировки по имени принят пользователем 2026-10-21 и включён в main через PR #322.

## Scope (только утверждённый пункт №2 UI-080)

- Колонка РЕЖИМ на вкладке История аукционов и поле Общие → Режим показывают один и тот же реальный путь определения победителя из сохранённых session/audit/spin фактов.
- Чистая Максимальная сумма, прямое Обычное колесо, прямое Выбывание, Максимальная сумма → Колесо при ничьей после фактического wheel spin.
- Если существующая история содержит Max Amount → standard/elimination wheel без события tie_wheel, форматировать как Максимальная сумма → Обычное колесо / Максимальная сумма → Выбывание. Для текущих сценариев это не меняет бизнес-логику.
- Для последовательных реальных вращений в разных форматах (standard/elimination) показывать смены по порядку, повтор одного формата подряд сворачивать. Изменение выбора формата БЕЗ реального нового spin не считать уже произошедшим этапом.
- Legacy снимок реального вращения без audit wheel может выступать историческим свидетельством. При отсутствии сведений не выдумывать вращения.
- Источники read-only: существующие auction_sessions, change_log (create/tie_wheel/wheel_format/wheel) и immutable wheel_verification_snapshots (spin_index/result_kind). Данные страницы читать пакетно, не делать 50+ N+1 запросов.

## Не менять

- Версия 1.0.8, schema 19, миграции, storage, RNG, проведение, денежные начисления, тексты других экранов и журнальных событий.
- Поиск, периоды, сортировку по дате, пагинацию 50, summary, прочие вкладки детализации.
- UI-080 шаг 3: условная видимость Проверка результата; шаг 4: расширенные audit-описания; UI-081: общий Журнал. Это отдельные этапы.

## Автоматические проверки

- Native Windows Regression Foundation включает отдельный tools/completed_auction_history_mode_path_smoke.py и все предыдущие регрессии.
- Проверяются чистый Max, выбранное без вращения tie-wheel, подтверждённый фактический tie-wheel, direct standard/elimination, реальные последовательности форматов и отсутствие ложных этапов, legacy verification snapshot без audit, отображение таблица=Общие.
- Обязателен Publication wording, реальная сборка Inno Setup, установка/запуск, OBS/Chromium.

## Ручная Windows проверка

1. Установить проверочный ZIP поверх принятой 1.0.8, проверить сохранность игр, настроек и архива.
2. Чистый завершённый Max Amount должен показывать Максимальная сумма без перехода к колесу.
3. Завершённые прямые варианты: Обычное колесо либо Выбывание соответственно (при наличии таких записей).
4. Если был реальный Max Amount с ничьей через колесо: Максимальная сумма → Колесо при ничьей. Если нет, новая сессия ради этой проверки не требуется: сценарий покрыт автоматикой.
5. Если между реальными вращениями менялся формат, отобразятся фактически использованные форматы в нужном порядке; не последняя выбранная опция сама по себе.
6. Для каждой просмотренной записи сверить РЕЖИМ в основной таблице с Общие → Режим. Проверить Лоты, События, Проверка результата, поиск, периоды, оба варианта сортировки по дате, F5, узкое окно, OBS, Музыку, Журнал.

После отдельного подтверждения пользователя продвинуть ровно проверенные исходные blob SHA в main с Windows и postmerge regression; не публиковать релиз.
